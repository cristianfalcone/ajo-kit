- Kind: duplication — Verifier confidence: high

**Evidence.** Three parallel copies of the same protocol in five files. (a) Placement closures reading content.dataset: popover.tsx:139-144, tooltip.tsx:166-171, select.tsx:316-320, dropdown-menu.tsx:231-235, input-date.tsx:380-385 are line-for-line identical modulo defaults — e.g. popover.tsx:141 `sideOffset: () => Number(popover.content?.dataset.sideOffset ?? 4)` vs select.tsx:318 `... ?? 6` vs tooltip.tsx:168 `... ?? 0`. (b) Content parts stamping the dataset the closures read back: popover.tsx:553-566, tooltip.tsx:369-381, select.tsx:1129-1143, dropdown-menu.tsx:466-482, input-date.tsx:1269-1286 all render `data-align / data-align-offset / data-collision-padding / data-side-offset / data-side-preference / data-state={open?'open':'closed'} / id={ctx.contentId} / popover=... / style={popupStyle(style)} / tabindex="-1"` plus the `setContent`+`callRef` ref composition. (c) Trigger parts: popover.tsx:370-390, dropdown-menu.tsx:396-421, select.tsx:913-940, dialog.tsx:205-225, input-date.tsx:1222-1244 all render `aria-controls={ctx.contentId} aria-expanded data-state id={id ?? ctx.triggerId} ref={setTrigger+callRef}` and a `callHandler(onClick)/defaultPrevented`-guarded toggle. consolidation.md §B4 already prescribed attr bags; the slice-2 status notes list everything shipped and attr bags are absent. ajo-cloves README documents attr bags as the house idiom (the `label` clove returns them).

**Proposal.** In floating.ts (the module that already owns this protocol), add three helpers and spread them: (1) `datasetPlacement(content: () => HTMLElement | null, defaults: { side, align?, sideOffset, alignOffset?, padding, constrain? }): FloatingPlacement` — one reader, per-family defaults stay as the options; (2) `contentAttrs({ side, align, sideOffset, alignOffset, collisionPadding, open, id, popover, style })` returning the data-* stamp + `popupStyle(style)` + `tabindex: '-1'` for JSX spread; (3) `triggerAttrs({ open, contentId, triggerId, id, haspopup })` returning the aria/data/id bag (families keep their own onclick policy and role deltas). Each of the five roots then passes `placement: datasetPlacement(() => pop.content, { side: 'bottom', sideOffset: 6, padding: 8 })` and each part becomes `<div {...contentAttrs(...)} ...family deltas>`. Deletes ~150-200 lines of copies and makes new floating families (the next Select-like) correct by construction.

**Verifier.** Verified against current code: the placement-closure blocks (popover.tsx:138-145, tooltip.tsx:165-172, select.tsx:315-321, dropdown-menu.tsx:230-236, input-date.tsx:379-386), the content-part dataset stamps (popover.tsx:547-570, tooltip.tsx:365-389, select.tsx:1128-1146, dropdown-menu.tsx:465-486, input-date.tsx:1268-1289), and the trigger bags (popover, dropdown-menu, dialog, input-date; select is a partial match) all exist as cited — three parallel copies of one protocol, differing only in defaults and small per-family deltas. Crucially, ai/consolidation.md §B4 (lines 119-128) prescribes exactly the proposed triggerAttrs/contentAttrs builders as MEDIUM priority, line 321-322 scopes 'attr bags' into slice 2, and the slice-2 Status entry (lines 360-380) lists everything shipped without them — the only recorded deferral there is the clove promotion, not §B4. So the behavior is not a recorded deliberate decision; it is the plan's own item that silently didn't land despite the 'Phase: COMPLETE' stamp. grep confirms no triggerAttrs/contentAttrs/datasetPlacement helper exists anywhere in packages/. The proposal net-simplifies: floating.ts already owns FloatingPlacement, popupStyle, and the ids the bags stamp; the bags are plain attribute objects (data-*/aria-*/id/popover/style/tabindex) with no event wiring, so SSR via ajo/html is unaffected and no layering is crossed (helpers stay ajo-ui-internal, consistent with the deferred clove promotion). Roughly five copies of three blocks collapse onto one helper trio for a clear net line reduction and a single canonical definition of the dataset read-back protocol. Minor evidence inaccuracies that do not change the verdict: SelectTrigger uses aria-controls={listId} with role=combobox (not contentId); SelectContent stamps no id; TooltipContent has no tabindex; dropdown-menu's padding is a hard-coded () => 4 and its content omits data-collision-padding — all per-family deltas the parametrized helpers must (and can) accommodate.

**Revised proposal.** As proposed (datasetPlacement / contentAttrs / triggerAttrs in floating.ts, spread with family deltas kept local), with corrections from the actual code: (1) triggerAttrs must take the controls id as a parameter, not assume ctx.contentId — SelectTrigger points aria-controls at listId (listbox) with role=combobox per APG; dialog opens (never toggles) and dropdown-menu passes focus intent, so the click policy stays per-family as the finding already says. (2) contentAttrs must make id, tabindex, popover mode, and the data-{family}-content marker optional/parametrized: SelectContent currently stamps no id, TooltipContent has no tabindex, and modes differ (manual/auto/arg). Decide deliberately whether unification normalizes these (e.g. giving SelectContent an id is arguably a fix) rather than letting the helper change them silently. (3) datasetPlacement needs the dropdown-menu case: its padding is a constant 4 and its content doesn't stamp data-collision-padding — a dataset read with default 4 is behavior-equivalent, but note it in the migration. Record the outcome as the §B4 closure in ai/consolidation.md Status.

**Resolution (2026-07-11).** Implemented as an internal seam in `floating.ts`, with three pure builders covered by focused tests. Five roots now use the live `datasetPlacement` reader; the two Popover modes plus Tooltip, Select, DropdownMenu, and InputDate use `contentAttrs`; and both hover triggers plus Popover, Select, DropdownMenu, InputDate, and Dialog use `triggerAttrs`. The content/trigger bags own setter-before-caller ref composition, and `floating()` now adopts an explicit content id just as it already adopted trigger ids, keeping `aria-controls`/`aria-describedby` coherent. Family policy remains local: Select controls `listId`, Dialog opens rather than toggles, DropdownMenu retains input-modality focus intent and constant padding 4, Tooltip keeps reader fallback sideOffset 0 while stamping 8, Tooltip content still has no tabindex, Select content still owns no generated id, Dropdown content still stamps neither collision padding nor JSX data-state, and hover triggers keep their distinct expanded-state ARIA. Public stories assert literal content-id adoption for Popover, Tooltip, DropdownMenu, and InputDate plus trigger/content relations for those families and Dialog; existing Select coverage pins its listbox exception.

### C1 [high] Ungated host listeners crash ajo/html SSR in 13 stateful roots

- Kind: robustness — Verifier confidence: high
- Files: packages/ajo-ui/src/accordion.tsx, packages/ajo-ui/src/carousel.tsx, packages/ajo-ui/src/command.tsx, packages/ajo-ui/src/context-menu.tsx, packages/ajo-ui/src/dropdown-menu.tsx, packages/ajo-ui/src/menubar.tsx, packages/ajo-ui/src/navigation-menu.tsx, packages/ajo-ui/src/radio-group.tsx, packages/ajo-ui/src/resizable.tsx, packages/ajo-ui/src/select.tsx, packages/ajo-ui/src/slider.tsx, packages/ajo-ui/src/tabs.tsx, packages/ajo-ui/src/toggle-group.tsx

**Evidence.** The ajo/html protocol host has only signal/next/return/throw (D:\ajo\html.js:99-114) — no addEventListener. Ungated setup-phase calls: accordion.tsx:140, carousel.tsx:220, command.tsx:190, context-menu.tsx:107, dropdown-menu.tsx:289 and :804, menubar.tsx:148, navigation-menu.tsx:120 and :157, radio-group.tsx:73, resizable.tsx:218-219, select.tsx:457, slider.tsx:224, tabs.tsx:120, toggle-group.tsx:130 — all `this.addEventListener(..., { signal: this.signal })` with no DOM gate. Verified empirically: a vitest run of `render(jsx(Tabs|Accordion|ToggleGroup, ...))` through ajo/html throws `TypeError: this.addEventListener is not a function` while Toolbar (gated) passes. The house pattern already exists twice: toolbar.tsx:114 `if (isDom(this)) { this.addEventListener(...) }` and input-date.tsx:604-606 `const listen = (type, handler) => { if (domReady) this.addEventListener(type, handler, { signal: this.signal }) }` with the comment 'The ajo/html host is protocol-only: all browser wiring is client-only.' radio-group.tsx:74/79 additionally queues `queueMicrotask(() => syncRadioGroup(this))` which would also touch querySelectorAll on the protocol host.

**Proposal.** Promote input-date's `listen` helper to a shared primitive — either `listen(host, type, handler)` in utils.ts next to isDom, or a clove in ajo-cloves (cloves are the SSR-inert-by-shape layer; rule 6 of the clove contract already mandates exactly this guard) — and route all 15 call sites through it. Add one ajo/html smoke test that renders every exported root, so the whole class of regression is caught.

**Verifier.** Verified against current code and reproduced empirically. The ajo/html protocol host (D:\ajo\html.js:99-114) exposes only signal/next/return/throw; its catch re-throws setup-phase errors via iterator.throw, so nothing swallows the TypeError. All 16 cited this.addEventListener sites across the 13 files exist at the exact cited lines, in setup phase, ungated. A vitest run confirmed ssr(jsx(Tabs)), Accordion, and RadioGroup all throw 'TypeError: this.addEventListener is not a function' while gated Toolbar passes. radio-group.tsx:79's queueMicrotask(syncRadioGroup(this)) additionally reaches unguarded querySelectorAll (async crash path). This is not a design decision — ai/cloves.md:407-418 records the OPPOSITE doctrine ('imperative host writes must be isDom-guarded; all browser wiring is client-only') from a previously fixed SSR crash of the identical class (dataset writes in checkbox/toggle/input-otp, with tests/unit/ssr-host-writes.test.ts as precedent); these listener sites are the same sweep left unfinished. SSR via ajo/html is a first-class ajo-kit pathway and the app's src/ui layer re-exports these roots, so real pages crash. worthIt: the fix is a tiny shared helper plus mechanical call-site rewrites that each get SHORTER (listen(this, type, fn) vs this.addEventListener(type, fn, { signal: this.signal })), fixing 13 crashing roots — a correctness fix mandated by recorded doctrine, not stylistic. Layering holds: a listen helper in ajo-ui/src/utils.ts next to isDom is base-layer behavior (only visual styling is excluded from base), no JSX, no theme involvement.

**Revised proposal.** Add `listen` to packages/ajo-ui/src/utils.ts next to isDom — `const listen = (host, type, handler, opts?) => { if (isDom(host)) host.addEventListener(type, handler, { ...opts, signal: host.signal }) }` (promoting input-date.tsx:604-606's local helper) — and route the 16 ungated call sites in the 13 files through it; migrate toolbar.tsx and input-date.tsx too so the pattern is single-sourced. **Resolution (2026-07-10).** Implemented. `listen` now lives in `packages/ajo-ui/src/utils.ts`, guards protocol-only SSR hosts, and composes a caller signal with the host lifecycle through `AbortSignal.any`. All 25 base-layer listener sites use it; DOM-only microtasks in Command, RadioGroup, and Select are gated too.
